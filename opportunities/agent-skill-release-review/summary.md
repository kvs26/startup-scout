# Agent skill release review for small AI delivery teams

A small software consultancy has a set of **agent skills**: folders of instructions and scripts that tell an AI coding agent how the team handles jobs such as reviewing a client's pull request or preparing a deployment. A consultant edits one skill to improve it for a new client. The team can see the changed text in Git, but the person approving it still has to answer a harder question: when colleagues use the new version, will the agent choose it at the right time, do the required work, and avoid actions the team did not approve? A [consultant team's reviewer described this as an informal bottleneck](research.md#e001). The proposed first market is small Indian software or AI implementation teams already maintaining their own Claude Code skills. Their willingness to buy is unknown.

The offer would be a **local release-review tool**. It would take a proposed skill change and a few examples chosen by the team, run the old and new versions in separate test workspaces, and produce a short report for the reviewer. The report would show which examples triggered the skill, what files or commands changed, whether agreed checks passed, and where a person needs to inspect the actual output. It would leave the approval to the team. It would use an existing evaluation engine where practical rather than claim to invent a new way to grade agents.

**Imagined example:** A consultancy has a `client-release-check` skill. Priya changes it to say that the agent must ask for approval before preparing a production deployment. The lead selects six past release requests, including one with missing test results and one that must stay in a draft state. The tool runs each request with the old and proposed skill in disposable copies of a sample repository. Its report shows that the new skill asks for approval in five cases, but tries to continue in the missing-results case. The lead opens that run's trace, rejects the change, and asks Priya to fix it. This sequence illustrates the offer; no observed team has used or paid for it.

The consultant writing skills would use the tool. A team lead or operations reviewer would approve the change. The proposed payer is the consultancy owner or engineering lead, paying a monthly fee per active team or client project for the software and updates. An initial setup fee could cover connecting a repository and selecting test examples. **No price, budget holder, payment terms, or repeat purchase has been observed.**

## The customer's work and why this problem matters

Agent skills are normally stored as files, so teams can review their text in a Git pull request. That catches wording changes, but a model may fail to load the skill, choose a neighboring skill, skip a step, or behave differently when a model or repository changes. The reviewer needs to know what the agent *did* on representative requests, not just what the instructions say. OpenAI's [evaluation guide](research.md#e013) describes checking invocation, actions, outputs, and artifacts; an [Anthropic community discussion](research.md#e002) asks how maintainers tell whether a skill or pull request improved those behaviors.

The clearest direct workflow account is a self-described operations reviewer whose consultants contribute skills to a shared GitHub repository. They check scope, missing data, metrics, and human review, while asking how to test variable output without blocking contributors [E001](research.md#e001). Separate GitHub reports show that even test results can be misleading: one reported failure turns a crashed run into an apparently successful negative test [E003](research.md#e003), and another reports a skill being invoked while the test records a miss [E004](research.md#e004). These are specific reports about a tool, not evidence that all teams face the same problem or that those bugs still affect every release.

An India-oriented discussion includes a team that already commits its skills and reviews Git diffs [E005](research.md#e005). That is a sensible free method and may be enough. The public evidence does not show how often small Indian consultancies ship skills, whether errors have cost them money, or who would pay for an extra check.

## What the first version would do

Start with Claude Code skills in a Git repository. During setup, a team member chooses one skill and adds a small set of past or synthetic requests, sample files, and checks. A check could ask whether the agent used the skill, created a required file, avoided a forbidden file change, or left a release in draft when an input was missing. The software runs the old and proposed skill against the same examples in isolated workspaces, records the model and tool versions, captures commands and changed files, and labels execution errors separately from skill failures. It generates a readable Markdown report attached to the pull request or saved locally. A reviewer opens the underlying trace when a result is ambiguous and explicitly approves or rejects the skill change.

The first version should keep tests on the customer's machine or CI account, using the customer's agent/model credentials. It should use dummy or customer-approved fixture data; sending confidential client files to a new hosted service would create a separate trust and security obligation. A person must choose meaningful examples and decide whether the actual output is acceptable. A green report cannot prove that every future request is safe. If a skill can send messages, deploy, delete, or spend money, the relevant tool or API must enforce permission; text in a skill and a test report are insufficient, as replies to [E001](research.md#e001) point out. Automated permission enforcement is outside this first product.

## Why someone might buy it and keep using it

The possible paid value is quicker, more consistent review when several consultants change client-specific skills. A manager could approve a change from a short evidence report, and keep a record of what was checked for that version. Another use arises with each important skill revision, model change, or new client workflow. This recurrence is a product hypothesis, not measured use. A team with only a few stable skills might run a free test occasionally and never need a subscription.

The proposed charge is per active team or project per month, with a possible one-time setup charge. The customer would still pay for its Claude/model access and any CI minutes. The price must be tested against the team's existing cost of review, which has not been measured. A published training offer of ₹75,000 per day in India [E010](research.md#e010) is a *different service's asking price*, not evidence for this product's fee.

## Evidence and existing alternatives

The evidence supports a narrow observation: some maintainers care about testing and reviewing skills, and at least one consultant team has an informal approval process. It does **not** yet support an unmet paid market in India. The strongest contrary finding is that the core tests already exist. [Promptfoo](research.md#e006) documents side-by-side old/new skill tests, trigger assertions, output checks, repeated runs, and trace inspection; its [Community edition](research.md#e011) is free for local use. [Anthropic skill-creator](research.md#e007) offers evals and comparisons. [Tessl](research.md#e008) offers a skill registry, versioning, activation checks, and before-and-after evaluations. Ordinary Git review is a working manual option for at least one reported team [E005](research.md#e005).

The proposed opening is a smaller team's *review handoff*: help an author choose useful examples and give an approver one clear release decision page without setting up a broad evaluation platform. That benefit is unproven, and Promptfoo may already be simple enough once configured. If a team can do the same job comfortably with Git and free Promptfoo, this product has no clear reason to exist for them. Reported bugs in Anthropic's tool are reasons to verify test infrastructure carefully, not a durable competitive advantage; the vendor can fix them.

## How to find the first customers

Public GitHub repositories and discussions in r/developersIndia show people maintaining shared skill files and asking about cross-agent setup [E005](research.md#e005), [E009](research.md#e009). India-based Claude Code training and implementation firms, such as the provider documented in [E010](research.md#e010), identify a nearby service market. A practical research route is to find small firms with several maintained skill files, then ask to observe one recent skill change and its approval process. The public repository or firm site supplies a route to investigate, not a relationship, buyer, or permission to contact anyone. Some firms may sell equivalent review work themselves. We do not know the relevant manager's buying authority, confidentiality rules, procurement steps, or whether written outreach will reach them.

## What building and running it would require

The technical work is a reliable local runner, isolation for each test, detection of which skill was used, capture of tool actions and files, honest treatment of crashed/partial runs, and a report a reviewer can understand. Reusing Promptfoo could reduce the runner work, but compatibility with the selected Claude Code version and customer environment must be tested. The initial setup still needs someone to turn real client requests into safe examples and decide which outcomes matter. Each customer's skills may refer to different commands, integrations, and secrets; onboarding cannot be fully automated until those patterns are understood. Support would include failed runs, tool upgrades, model behavior changes, and unclear results. The founder would need to reproduce failures independently rather than rely only on an agent's explanation.

The cheapest architecture is local software with no customer data hosted by the founder. Promptfoo advertises free local evaluation [E011](research.md#e011), while GitHub includes plan-dependent private-repo runner minutes and charges the repository owner for overages [E012](research.md#e012). The customer's model calls are additional. For scale, **an assumed** eight examples × two skill versions × three repeats means 48 agent runs for one proposed release; model tokens, run length, and exact provider pricing determine the bill. This is a workload illustration, not a cost estimate. The founder's own prototype would also consume model access and time. Packaging, documentation, billing, support, expert review, and any future hosted dashboard remain unpriced. The ₹5,000/month founder budget looks compatible with exploring a local prototype using limited runs, but **paid reliability and support within that budget are unassessed**. No revenue or margin estimate is defensible yet.

## Domain knowledge needed

For conversations and a prototype, learn the agent-skill file format and when a runtime loads a skill. The `name` and `description` can affect whether it is selected, while scripts and references can change what it does. Anthropic's [skill structure and security guidance](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) and OpenAI's [evaluation guide](research.md#e013) are starting points. You need to explain the team's path from authoring a skill to approving a pull request and colleagues using it, because a report delivered after the wrong decision point is useless.

Next, learn test fixtures (safe sample repositories and inputs), positive and near-miss trigger cases, deterministic checks versus human quality judgment, and how to read tool traces. These determine whether the report catches a real regression or merely displays a reassuring score. Then learn isolation, credentials, side effects, and the difference between a test failure and an agent failure; [reported false verdicts](research.md#e003) show why this matters. For reliable paid delivery, an experienced engineer should review runner isolation and failure classification. A security specialist would be needed before claiming the product vets untrusted skills or enforces permissions; those claims are outside the first offer.

You already know what it is like to work with agent skills as a user. Team approval practice, evaluation design, safe execution, and reviewer needs remain unassessed. A practical learning exercise is to take one of your own low-risk skills, write three requests where it should run and two nearby requests where it should not, then use a disposable repository to compare current and edited versions with Promptfoo. Record what the agent actually read and changed, deliberately make one run fail, and explain the result to an experienced engineer. Afterward you should be able to say which result is a skill regression, which is a broken test, and which still requires human judgment. The time to reach paid-delivery competence is unknown; do not assume it fits your preferred few weeks of domain learning.

## What happens next

**Recommendation:** Investigate the approval workflow with a few relevant teams before building a product. The strongest reason to continue is a real reported review bottleneck in an area you know personally. The strongest reason to decline is that free, capable alternatives already test skills, and we have no evidence that a small Indian team will pay for a simpler review handoff. Continue only if an approver shows repeated costly work that Git plus Promptfoo does not solve comfortably. Otherwise leave this idea.

**User selection:** None recorded.

**Next unresolved question:** On a recent, real skill change, where does the reviewer spend time or make mistakes *after* using their existing tools, and would a short local release report change the approval decision? A permitted walkthrough and comparison with free Promptfoo would answer more than another general web search. The founder has no confirmed team willing to show this work.

## Research limits

This round read public English-language practitioner accounts, GitHub issue reports, first-party tool documentation, India-oriented discussions, a local service offer, and supplier billing terms. It did not inspect a customer's private skill repository, run current versions of the competing products, verify whether the reported bugs were fixed, price model usage, or interview a payer. Reddit identities and business circumstances are unverified. India-oriented posts do not prove the posters work in India, and an India-based consultancy's offer does not prove sales. The round stopped because the recommendation now turns on actual review time, buyer willingness, and usability against free alternatives; additional general tool listings would mainly repeat established competition.
